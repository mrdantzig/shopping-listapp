# 코드 리뷰 (버그/정확성 + 성능) + 테스트 실행

이 스킬은 두 가지를 한다: (1) 테스트 스위트가 있으면 실제로 실행해서 통과 여부를 확인하고, (2) 버그·정확성 문제와 성능 문제를 정적으로 점검한다. 스타일, 네이밍, 가독성, 보안 취약점은 이 스킬의 범위가 아니므로 지적하지 않는다 (보안은 `/security-review`, 스타일/단순화는 `/simplify`를 안내한다).

## 1. 테스트 실행

먼저 프로젝트에 실행 가능한 테스트가 있는지 확인한다. 예시:
- `package.json`의 `scripts.test` (npm/yarn/pnpm test)
- `pytest.ini`, `pyproject.toml`의 `[tool.pytest]`, `setup.cfg`의 `[tool:pytest]` (pytest)
- `go.mod` (`go test ./...`)
- `Cargo.toml` (`cargo test`)
- `Makefile`의 `test` 타깃

**있으면**: 해당 명령을 Bash로 실행하고 전체 출력을 확인한다.
- 실패한 테스트가 있으면 각각을 파일/라인과 함께 findings로 만든다 (`category: correctness`, `verdict: CONFIRMED`, `failure_scenario`에 실패 원인과 테스트 출력 근거를 적는다).
- 전부 통과하면 통과 개수를 사용자에게 보고하고 2단계(리뷰 대상 정하기)로 넘어간다.

**없으면**: 테스트 스위트가 없다는 사실을 사용자에게 그대로 알린다. 테스트를 새로 만들지는 않는다 — 사용자가 명시적으로 요청하지 않는 한 범위 밖이다. 이후 2단계(리뷰 대상 정하기)부터 정적 리뷰만 진행한다.

## 2. 리뷰 대상 정하기

인자(`$ARGUMENTS`)로 파일/디렉토리 경로가 주어지면 그것을 대상으로 한다.

인자가 없으면 다음 순서로 대상을 정한다:
1. 이 디렉토리가 git 저장소이면 `git status`로 변경 사항을 확인한다.
   - staged/unstaged 변경이 있으면 `git diff HEAD`(추적 파일) + 새로 추가된 untracked 파일을 대상으로 한다.
   - 변경 사항이 전혀 없으면 가장 최근 커밋(`git diff HEAD~1 HEAD`)을 대상으로 한다.
2. git 저장소가 아니거나 커밋 이력이 없으면, 프로젝트 내 소스 파일 전체를 대상으로 한다 (node_modules, dist, build 등 생성물 디렉토리는 제외).

대상 파일이 너무 많으면(대략 15개 이상) 사용자에게 전체를 볼지, 핵심 파일 위주로 볼지 묻는다.

## 3. 코드 읽기

대상 파일을 Read로 직접 읽는다. 변경분만 보지 말고, 수정된 함수/블록이 호출되는 곳이나 관련 상태(전역 변수, 공유 데이터 구조 등)까지 Grep으로 따라가 문맥을 확보한다. 짐작으로 판단하지 않는다.

## 4. 점검 기준

**버그/정확성**
- 로직 오류: 조건문 반전, off-by-one, 잘못된 연산자, 잘못된 비교
- 엣지 케이스 누락: 빈 배열/문자열, null/undefined, 0, 음수, 경계값
- 상태 불일치: 낙관적 업데이트와 실제 저장소(localStorage, DB 등) 간 불일치, race condition
- 잘못된 비동기 처리: await 누락, 처리되지 않은 Promise rejection, 콜백 순서 가정 오류
- 타입 불일치로 인한 런타임 오류 가능성

**성능**
- 불필요하게 반복되는 연산 (루프 안에서 매번 DOM 쿼리, 매번 재계산 등)
- O(n^2) 이상으로 커질 수 있는 패턴을 O(n)으로 바꿀 수 있는 경우
- 불필요한 리렌더링/재생성 (매 호출마다 새 객체/함수 생성 등, 프레임워크 사용 시)
- 과도한 메모리 사용 (무한정 커지는 캐시/배열, 정리되지 않는 이벤트 리스너/타이머)

각 항목마다 "이 코드가 실제로 이 문제를 일으키는가"를 코드를 다시 읽어 검증한다. 확신이 없으면 findings에 넣지 않거나 verdict를 PLAUSIBLE로 표시한다. 억지로 문제를 만들어내지 않는다 — 문제가 없으면 findings는 비어 있어도 된다.

## 5. 결과 보고

1단계에서 만든 테스트 실패 findings와 4단계의 정적 리뷰 findings를 합쳐 `ReportFindings` 도구로 한 번에 보고한다. 각 finding은:
- `file`, `line`: 해당 위치
- `summary`: 결함을 한 문장으로
- `failure_scenario`: 구체적인 입력/상태 → 잘못된 출력/충돌로 이어지는 시나리오
- `category`: `correctness` 또는 `performance`
- `verdict`: 코드를 다시 읽어 확인했으면 `CONFIRMED`, 근거는 있지만 완전히 확신할 수 없으면 `PLAUSIBLE`

가장 심각한 순서로 정렬한다. 문제가 없으면 빈 배열로 보고한다.
